# 講義設計原則 (fp を中心に; 新章・改稿時の設計チェックリスト)

散文の文体でなく内容の組み立ての規範. 修正指示が繰り返しここに帰着してきたもの.

- **数学 ∥ Haskell ∥ 対応の三本立て**: 新概念は (1) 数学的対象の定義 (既習語彙で: 集合→代数→圏),
  (2) Haskell での実現, (3) 対応表・可換図式で結ぶ, の 3 点を揃える. Haskell 側だけの説明や,
  土台のない圏論用語の唐突な導入をしない.
- **抽象化は具体の後に 1 段ずつ**: 一般定義・型クラスの前に具体的構成を手で作らせる
  (具体 2 例 → 一般定義 → Haskell の機構, の順を既定にする).
- **誤概念の予防は warn でなく構成で**: 誤解を生む導入順序・最初の例そのものを変える.
- **比喩の採用基準 = 全実例に同じ言葉が通ること**: 部分的にしか成り立たない比喩 (「箱」等) は
  不採用. 定義から導かれた読み方を使う. 通った比喩でも, view §A8 のとおり再参照ハンドル化してはならない.
- **少数の例を深く使い回す**: 新概念に新例を持ち込まず, 既出の例が章をまたいで新しい見方で
  再登場する形にする. 図も同じ系列を発展させる (図0〜図4 の系列).
- **名前と記法の照合可能性**: 図の注記は定義の組と同じ成分名 (Ob= / Mor=) を使い, 訳語は分野の
  慣用に従い (「矢」でなく「射」), 操作にも命名して再利用する (「俯瞰」).
- **図でわかりやすさを保つ**: 具体的な圏・構造が出てきたら図を入れる.
- **代数例の体裁**: 組込型より自作の列挙型 (`data Bool2 = T | F`) を優先し, 各実装に対応する数式を
  KaTeX で併記する. 数式の演算に対応する名前付き 2 項演算子を先に定義し, それで型クラスの
  メソッド (`(<>)` 等) を与えて数式↔コードの対応を明示する. コード内の演算子は ASCII
  (`|+|` `.&.` 等). Unicode 数式記号 (∧ ∨ ⊕) は本文・コメントの数式側のみ.
- **課題は algebra-first**: 演習・課題は「シグネチャ → 公理 (観測子×構築子) → 実装 → 公理の
  QuickCheck property 化 → 未規定 (部分関数) の考察」の順で設計する. アプリ・プロダクト起点に
  しない. テンプレの正本は fp12 導入節.
- **エラーは専用列挙型を第一候補に**: 失敗の理由は `Either String` の生文字列でなく, 起こりうる
  エラーを列挙した直和型 + `render :: SomeError -> String` で表す. String 版は「手軽だが網羅検査が
  効かない」副例として残す. (専用型は derived `Show` でも ASCII になり, 日本語 String の
  エスケープ問題も回避できる. エスケープ出力例は必ず実 GHC で確認する.)
