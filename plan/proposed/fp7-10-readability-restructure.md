# fp7〜fp10 本文の簡素化と読解経路の再構成

## メタ情報

- **状態**: proposed
- **作成日**: 2026-07-23
- **最終更新**: 2026-07-23
- **対象**: `lectures/fp/fp7.md`〜`fp10.md`
- **関連計画**: [fp-v2-unified-rebuild.md](fp-v2-unified-rebuild.md), [fp-typeclass-monad-arc.md](fp-typeclass-monad-arc.md), [fp-examples-verification.md](fp-examples-verification.md)

## 実施形態 (2026-07-23 ユーザ決定)

本計画は **単独では実施しない**. [fp-v2-unified-rebuild.md](fp-v2-unified-rebuild.md) の Phase B (章構成変更) との**統合作業**として, 2026-08-10 以降に実施する (同日付の Todoist タスクが trigger. plan-lifecycle 規約の dated-task park). 特に **fp7 は Phase B1 で 2 章 (Ch5 = 集合部 / Ch6 = 関係部) に分離する** ため, 本計画の Phase 1 (fp7) は分割後の 2 章の設計に吸収される. Phase 0 (2 層機構の評価) と Phase 2〜4 の観点は, 統合作業時の readability 側チェックリストとして用いる.

## 概要

正確さを維持したまま, fp7〜fp10 の各章に **最初に読む本筋** と **必要時に戻る数学的発展** の区別を設ける. 一度に4章を改稿せず, 各章について「個別検討 → 詳細差分の提示 → ユーザ承認 → 実装 → 検証」を完結させてから次章へ進む.

現行4章は合計 7,092 行あり, 個々の説明は充実している一方, 基本概念を初めて学ぶ読者が抽象的な補助線を本筋と区別しにくい. 本計画では完全版の教科書本文を正本とする既存方針を維持し, 内容を別資料へ分裂させず, 同じ章の note・発展節への再配置と重複説明の統合によって読解負荷を下げる.

## 動機

2026-07-23 の fp7〜fp10 正確性監査では, 重大・中程度の記述上の問題を修正した. その過程で, 正誤とは別に次の構成上の課題が確認された.

- 基礎概念を理解する前に, 量化・不動点・束・商・圏の圏など複数段の抽象化が連続する.
- 同じ概念を「直観」「一般定義」「圏論的再解釈」の複数箇所で説明し, 本筋の進行が長く止まる部分がある.
- `Functor` / `Applicative` / `Monad` の利用上の違いより, 圏論的な構成の説明が先に大きな比重を占める.
- 完全版として残す価値のある内容と, 初読時に必須の内容が見た目上ほぼ同じ重さで並んでいる.

## 既存計画との整合

### 維持する既決定

- 数学と Haskell を並列に示す.
- 構造を「組 + 法則」で説明する.
- 一般定義だけでなく具体例と実行可能なコードを置く.
- 完全版本文を正本とし, 短縮版を別ファイルとして二重管理しない.
- 演習見出し・アンカー・提出ファイル名の規約を維持する.
- Haskell コードブロックを変更した場合は対応 spec を同期し, `stack test` を通す.

### 明示的な競合

1. **fp9 の導入順**: 本計画の当初案「`map` / `Maybe` / `Tree` → `Functor` → 関手則 → 圏論」は, [fp-v2-unified-rebuild.md](fp-v2-unified-rebuild.md) で承認済みの「一点圏の関手 → 小さな圏の関手 → 一般定義 → `Functor`」と逆順になる. 既存方針を変更するため, fp9 の詳細検討時に独立した選択・承認を必須とする.
2. **fp10 の圧縮**: `lectures/fp/fp10.md` のモノイド対象節には未コミットの加筆がある. 内容を削除対象とみなさず, まず節内圧縮・発展 note 化・後置のいずれで保存するかを比較し, 明示承認後に編集する.
3. **fp10 の本筋順序**: 当初案の「利用の主線を先に通し, 圏論的説明を後置する」は, 確立済みの「新概念は数学的対象を先に (または並べて) 定義し, 対応で結ぶ」という設計と競合する (fp10 は 需要 → 手作り → 数学的構造 → 型クラス → 則 の律動で再構成済みで, fp9 も 2026-07-20 に同じ律動へ揃えてある). 本計画ではこの律動を **変更しない** ことを既定とし, fp10 の簡素化は数学節の内部圧縮と発展 note への切り出しに限る (Phase 4 参照).

## 設計原則

1. **本筋は1段ずつ進める**: その節で必要な抽象化だけを導入し, 2段先の一般化は発展へ送る.
2. **定義は一度だけ置く**: 後続箇所では短い要約とリンクで参照し, 同じ一般論を再展開しない.
3. **具体例を使い回す**: 新しい抽象概念ごとに例を増やさず, `Maybe`, リスト, `Frac`, `Moments` など既存例を再利用する.
4. **発展内容は削除より再配置を優先する**: 正確で有用な内容は note または章後半へ移し, 初読経路から外す.
5. **演習の学習目標を維持する**: 本文移動によって演習の前提が後置されないようにする. 番号変更は原則行わない.
6. **章ごとに land 可能にする**: 1章の変更が未承認の次章変更を要求しない構成にする.

## 章別の再構成候補

### Phase 0: 既存 2 層機構の強化で足りるかの評価 (全章共通・最初に実施)

本筋/発展の 2 層は既に機構として存在する: 各章冒頭の「講義で辿る道筋」note (本筋の並び + 「必要になったときに本文へ戻る節」のリスト) と `::: note` 発展ブロックである. 節の物理移動はアンカー・前後参照・流れを壊すリスクが最も高い操作なので, 各章の詳細検討では移動の前に次を評価する.

1. 道筋 note の本筋リストと実際の節構成のずれを洗い出す (fp7・fp8 に道筋 note が無ければ新設する).
2. 発展にあたる節・段落へ一貫したラベル (「発展:」prefix つき見出し, または note 化) を付けるだけで初読経路が成立するかを判定する.
3. 重複説明の統合 (設計原則 2) はラベリングと独立に実施できるため常に行う.

ラベリング + 統合で目標を満たす章では節移動を行わない. 満たさない章のみ, 差分提示と承認を経て移動へ進む. 「初読経路」の可視化手段 (note 化 / 見出し prefix / 折り畳み) は全章共通の決定として Phase 0 で確定する.

### Phase 1: fp7 — 型を集合として読むための最短経路

現行: 1,991 行.

初読の本筋を次の順に揃える.

1. 集合・要素と列挙型.
2. 直積型・直和型と数え上げ.
3. 再帰的データ型.
4. 関係 → 関数 → 演算.
5. 同値関係・順序関係.

再配置候補:

- 「述語と量化」は, 部分集合・関係の法則を読むための最小定義だけを該当箇所へ残す.
- 量化の有限全数検査, 一般的な内包表記の展開は参照節または note へ移す.
- 生成作用素 $\Phi$, 最小不動点, 始代数への予告は再帰型の発展 note としてまとめる.
- `type`, `newtype`, スマートコンストラクタは ADT の本筋後の「表現を安全にする道具」として一群にまとめる.

承認前に提示するもの:

- 現行見出し → 新見出しの対応表.
- 移動・統合・存置する段落の一覧.
- CH7-1〜7 の前提が変わらないことの確認.

### Phase 2: fp8 — 型クラスから Monoid と foldMap までを主線にする

現行: 1,739 行.

初読の本筋を次の順に揃える.

1. `class` / `instance` / `deriving` と `Show`.
2. `Eq` / `Ord` と法則.
3. `Semigroup` / `Monoid`.
4. `foldMap` と「法則を持つ利点」.
5. 次章の `Functor` への接続.

発展層へまとめる候補:

- `Enum` / `Bounded` / `Num` の細部.
- 半環, 加重集計, 差分集計, fusion.
- 束の一般論 (ブール代数の法則一覧そのものは本筋に残す).

本筋に残すもの (発展送りにしない):

- `Eq` の法則, `Ord` の全順序, `Semigroup` / `Monoid` の結合律・単位元律.
- 同値類・商集合と `Frac`: 「手書き `Eq` = どの同値関係で割るかの選択」は追加例ではなく, 型クラスの意味論という本章の中心テーゼ.
- 群と $\mathbb{Z}/7\mathbb{Z}$ (`mkZ7`): 章をまたいで再登場する基幹例 (fp9 で関手の実例として再利用) であり, 「少数の例を深く使い回す」原則の担い手.
- ブール代数の骨子: 第7章の集合演算との接続点 (詳細法則の一部は note 化可).

発展へ移すのは構造の一般化と追加例であり, 型クラスを安全に実装するための法則や章の中心テーゼではない.

承認前に提示するもの:

- `Eq` / `Ord` から `Semigroup` / `Monoid` へ進む接続文.
- 発展節へ移す範囲と, 各 Exercise CH8-K の配置案.
- `foldMap` を章の到達点にした場合のまとめ案.

### Phase 3: fp9 — 圏先行を維持して圧縮する

現行: 1,768 行.

初読前半の負荷を下げる手段は, 節の順序変更ではなく圧縮と発展層の明示に限る.

1. 圏と一点圏を短く定義.
2. `length` とリスト複写の2例で関手を構成.
3. 一般定義を短く回収.
4. `Functor` / 関手則.
5. 多相データ型の各モデル.
6. Cat・自然変換・関手圏は章後半の発展層として明示する.

リスク: `Functor` を使いたい読者が具体例に到達するまでの距離は残る. 道筋 note と発展ラベル (Phase 0) でどこまで縮むかを先に確認する.

**不採用の記録**: 「リスト・`Maybe`・`Tree` の具体的な `fmap` → `Functor` クラス → 圏論」という実用先行案も検討したが採用しない. 確立済みの設計原則 (具体的構成を型クラスより先に置き, 「関手 = コンテナの `fmap`」という誤概念を構成で防ぐ. 2026-07-20 承認の fp9 再構成でも追認) と逆順になるためである. 再提案する場合は `fp-v2-unified-rebuild.md` の設計原則の変更承認を先に得ること.

### Phase 4: fp10 — 律動を維持したまま数学節を内部圧縮する

現行: 1,594 行.

「需要 → 部品の手作り → 数学的構造 → 型クラス → 則 → モデル」という Applicative ∥ Monad の対称の律動は変更しない (「明示的な競合」3). 簡素化は次の範囲に限る.

- 緩モノイド関手の節: 定義・$\varepsilon$・$\mu$・法則・`pure` / `<*>` 対応の主張を本筋に残し, 補足的な議論は発展 note へ切り出す ($\varepsilon$ の身分と strength の note は 2026-07-23 時点で note 化済み).
- 「モナドは自己関手の圏におけるモノイド対象」の節: 対応表と律の対応を本筋に残し, 可換図式・一般定義の作法は既存の発展 note の形を維持する. 重複する説明があれば統合する (設計原則 2). 未コミット加筆は「明示的な競合」2 の手順で保存する.
- Kleisli 圏は `>=>` と結合律の理解に必要な最小範囲を本筋に残し, 圏としての一般説明を発展へ分ける.
- `forM` はリストモナドではなく走査の補足として節を分ける (2026-07-23 の監査反映で実施済み. 確認のみ).

承認前に提示するもの:

- 節ごとの「本筋に残す / note 化 / 統合」の段落単位一覧 (未コミット加筆を含む).
- 圧縮前後の概算行数と, 失われる説明がないことの確認.

## 実施手順と承認ゲート

各 Phase は次の手順を独立して繰り返す.

1. **個別検討**: 対象章を通読し, 重複, 前提依存, 演習との接続を段落単位で整理する.
2. **詳細案提示**: 見出し対応表, 移動対象, 削除候補, リスク, 変更規模を会話で提示する.
3. **明示承認**: ユーザの「進めて」「OK」等を得る. 他章の承認とは分離する.
4. **実装**: 承認された章・範囲だけを編集する.
5. **検証**:
   - `git diff --check`.
   - コードブロックを変更した場合, 対応する `fp-examples/test/Fp<N>/*Spec.hs` を同期し `cd fp-examples && stack test`.
   - 見出し・Exercise アンカー・章内リンクを確認.
   - 見出し・節名を変更した場合は, fp11・fp12 からの参照 (アンカーリンクと「〜の節」形式の文中参照) も grep で検査する.
   - 章の「講義で辿る道筋」と実際の本筋が一致することを確認.
6. **章単位の報告**: 変更内容, 移動した発展内容, 検証結果を報告してから次章の検討へ進む.

実施順は, まず **Phase 0** (全章一括の評価と可視化手段の確定) を行い, その後は依存関係に沿って **fp7 → fp8 → fp9 → fp10** とする. 先行章の用語やリンクが確定してから後続章を調整する.

- 同じ一般定義を複数箇所で再展開していない.
- 数学的定義と Haskell の対応が失われていない.
- CH7〜CH10 の Exercise 番号・アンカー・提出ファイル名が維持されている, または変更が個別承認され対応表がある.
- Haskell コード例と spec が同期し, 必須テストが通る.
- fp7〜fp10 の全 Phase 完了後, 本計画を `plan/landed/2026-<date>-fp7-10-readability-restructure.md` へ移動する.

## 未解決事項 / リスク

1. **簡素化の尺度**: 総行数の削減を目的にすると, 完全版教科書の価値を損なう. 行数は参考値とし, 主指標は「本筋を読む際に通過する節数」と「新概念を同時に要求する数」にする.
2. **fp9 の設計競合**: 案Aを採る場合は `fp-v2-unified-rebuild.md` の設計原則・確定骨子も先に更新する.
3. **fp10 の既存差分**: ユーザの未コミット加筆と重なるため, 段落移動前に差分を保存・一覧化し, 内容の黙示的削除をしない.
4. **アンカーの破損**: 見出し変更で生成 HTML のアンカーが変わる. 外部・他章参照のある見出しは原則維持し, 変更時はリンク検査を行う.
5. **コードの重複解消**: 同じ例を統合するとコードブロックの削除・変更が発生し得る. prose-only と決めつけず, 該当時は spec 同期を行う.
6. **既存計画の stale 化**: 各章の構成を確定した時点で, `fp-v2-unified-rebuild.md` と `fp-typeclass-monad-arc.md` の該当箇所も同じセッションで更新する.
