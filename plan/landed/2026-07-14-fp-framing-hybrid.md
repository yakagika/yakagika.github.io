## A: fp9/fp10 framing 改修メモ (起草 — レビュー対象)

### A-1. 方針 (handoff の合意事項の確認)

- 「数学的構造 → Haskell シンタックス」の**全面反転はしない**. 俯瞰の階段 (モノイド → 圏 Hask → 圏 Cat → 関手圏, 組 + 法則で台を持ち上げる) は本書最大の資産であり, 構造先行の背骨として温存する.
- 現行の 3 層のうち, モデル層 (fp9: Maybe/Either/リスト/Map/ツリー) と道具層 (fp10: Applicative/Monad) は**既に目的先行**なので現状維持. 改修対象は**枠組み層 (fp9: 圏・関手・自然変換・Cat・関手圏) だけ**.
- 改修の形 = 各節の冒頭に**「需要の矢印」を一段落**添える. 供給 (階段を上から降りてくる構造) と需要 (計算タスクが下から突き上げる要求) をその節の道具の地点で出会わせる.
- 文体規律: ですます調, 半角句読点, 全角ダッシュ不使用, 新規比喩なし. 参照は数学的内容の章参照のみ (提示の仕方に関するメタ参照は書かない).

### A-2. fp9 に足す「需要の矢印」文案 (5 節, 各 1 段落)

**(1) 「圏の定義」節の冒頭** (現行の「第8章では, モノイドを…」の段落の前):

> この節で作る道具が, どんな計算の需要に応えるのかを先に述べます. [第4章](fp4.html)以来, 私たちは `g . f` と書けば関数がつながり, `id` を挟んでも何も変わらないことを当たり前に使ってきました. プログラムを「小さな関数の合成」として設計するこのやり方を支えているのは, 結合律と恒等律という 2 つの法則です. 本節は, この「当たり前」を組 + 法則として明文化した構造に名前を与えます. それが圏です.

**(2) 「関手」節の冒頭** (現行の「[第8章](fp8.html)の準同型の章では…」の段落の前):

> まず需要側から入ります. [第4章](fp4.html)の `map f` は「リストの中身にだけ `f` を当てる」操作でした. 同じことを `Maybe` の中身にも, ツリーの中身にもしたい. しかも容器ごとに別々の書き方を覚えるのではなく, 「中身への適用」を 1 つの共通の操作として持ちたい. この需要に応える道具が, 本節の関手です.

**(3) 「自然変換」部の冒頭** (「型に依らない一様な変換」節, 現行の「関手が「圏どうしの変換」だとすれば…」の前):

> これも需要側から入ります. `Maybe a` の値をリストへ変換する `maybeToList` は, 中身の `a` が何型でも同じやり方で動いてほしい関数です. 中身には触れず「容器の形だけ」を替える変換を, 型ごとに書き分けずに一度で定義し, その一様さを型で保証したい. この需要に応えるのが自然変換です.

**(4) 「圏の圏 Cat」節の冒頭** (現行の「図3 のラベルには…」の前):

> この節の道具の需要は[第10章](fp10.html)で現れます. リストのリスト `[[a]]` や `Maybe (Maybe a)` のような「関手を 2 回適用した形」を, それ自体 1 つの対象として扱いたいのです (モナドの乗法 $\mu : T \circ T \Rightarrow T$ の材料になります). そのためには「関手どうしを合成する」演算が要ります. その演算が住む場所を, ここで作ります.

**(5) 「関手圏」節の冒頭** (現行の「図4 に 関手圏 と名前を付けたからには…」の前):

> 需要を先に述べます. `maybeToList` のような一様変換は, 部品として合成したくなります (変換した結果をさらに別の一様変換へ渡す). 変換どうしの合成が圏の公理を満たすなら, 変換の等式変形 ([第10章](fp10.html)のモナド則がその実例です) を圏の言葉で安全に行えます. それを確かめるのが本節です.

対象外: 「圏 Hask」「圏はモノイドの一般化」「最初の関手」「リストの世界への複写」「一般の定義」「リスト関手と fmap」は, 直前節からの連続で読める (需要文の重複挿入はかえって煩雑) ため追加しない.

### A-3. fp10 の手当て (2 点)

1. **地図テーブルの前傾配置**: 現在「Functor の復習」節の末尾にある地図 (層/できるようになること/足す自然変換/法則/クラス) を, 章冒頭 note の直後へ独立して移す. 復習節は「fmap は 1 引数専用で止まる」という需要の提示に専念させる.
2. **モナド側の「需要 → 要件 → 合流」三段の明示**: Applicative 側は実装済み (多引数の fmap が欲しい → 部品は μ と ε → 緩モノイド関手). モナド側は現在「需要 (依存する連鎖) → 手作り (andThen) → 正体」の並びで, **要件の一文が欠けている**. andThen 節の末尾に「必要なのは『中身を見て次の計算を作り, できた入れ子をひと重に潰す』演算だ」という要件の言明を 1 文足し, 正体の節でそれが $\mu \circ T(-)$ として回収されることを明示する.

## B: Traversable の追加 (未起草 — fp11 計画と統合して後日)

- 位置づけ = **Applicative の「需要側の回収」**. `traverse :: Applicative f => (a -> f b) -> t a -> f (t b)` は「独立エフェクトを走査して融合する」Applicative の実際の使い所.
- 「なぜ Monad でなく Applicative で十分か」(走査の形が入力コンテナで静的に決まり, 途中の値に依存しない) が Applicative の静的性・独立性の最良の実例.
- `sequenceA` / `traverse` を「構造をなぞって作用を集める」操作として提示. Foldable との対比を一節. State との traverse (静的な形 + 動的な状態, ラベル付け) を発展例に.
- 章立て (fp11 の後ろか独立節か) は Phase A5 = fp11 執筆計画 (plan/in-progress/fp-v2-unified-rebuild.md) と統合して構成案を提示する.
